# Fast Hands recorded starts

Each homepage entry has its own recorded-start key:

- 鴨沒漏補: `fast-hands`
- 玩具彈接接樂: `fast-hands-catch`
- 十回合對決: `fast-hands-duel`

These are best-effort new-run counts, not unique players, completed runs, or historical estimates. Each starts at zero until its first accepted event; `since` stays null until then. No old play history is inferred or copied.

## Exact boundaries

For duck, clicking 開始 only prepares the game. The first accepted official pointer press in the home area counts the run. Demo play, rejected/secondary pointers, duplicate pointer events, or clicking preparation buttons do not count. Interrupting that run, cancelling a mode-switch confirmation, retrying the interrupted current run, resizing, or restoring the same page from BFCache does not count it again. A completed success/failure allows a new count on the next accepted arm. Returning to demo ends the current attempt; starting a later official challenge can count anew. Result playback never counts.

For catch and duel, the first accepted idle-to-waiting transition of a new non-practice match counts once. Every practice and repeated practice is excluded. Further catch stages and all remaining duel rounds retain that single count. Paused-current-round retry, cancel-switch/resume, result viewing, and playback do not count. An explicit new official match after a completed result gets its own run ID.

## Protocol and limits

`public/games/fast-hands/play-counts.mjs` is a separate reporter using the existing anonymous start protocol. It uses only the supplied window's fetch, storage, crypto and timers, so tests and local QA can intercept it before application startup. Gameplay never awaits the request.

The request contains only game, anonymous device UUID, run UUID, and start timestamp. Existing `pf-leaderboard-device-v1` storage is reused when valid. A failed request can be retried once after 2.5 seconds for network errors, HTTP 429 or HTTP 503; each attempt has a five-second timeout and reuses identical payload bytes/run ID. There is no offline backlog, polling, fingerprint, nickname, score or automatic leaderboard submission.

Backend admission remains unchanged: exact origin and feature gate, UUIDv4 and timestamp validation, 1 KiB streamed body bound, atomic receipt/total update, same-ID dedupe, conflicting-payload rejection, two-second game cooldown, 100 events per device/day, 10,000 total events/day, and bounded seven-day receipt cleanup. Rate limiting, network failure, blocked storage or crypto can undercount; none blocks gameplay. GET totals can remain cached for 30 seconds. Unavailable totals must remain distinct from zero.

## Existing schema and configuration

No migration or new database is required. Both `play_count_totals.counter_key` and `play_count_receipts.counter_key` are unrestricted TEXT in the existing `worker/play-counts/002.sql`. The counter primary key already includes `(scope,counter_key)`. Only the `/starts` allowlist and GET-total key list are extended. Existing leaderboard tables, score rules and configuration are unchanged.

The checked source configuration already routes `/api/play-counts*` through the Worker, sets `PLAY_COUNTS_ENABLED` to true for the existing QA preview, and binds its existing QA D1 database and trusted origin. This is a source/configuration check and an in-memory schema test, not a claim of a live remote database inspection. No remote SQL or counter POST was executed.

## Local verification

Run:

```sh
node --test tests/fast-hands/play-counts-*.test.mjs tests/play-counts-*.test.mjs tests/nine-play-counts.test.mjs
```

The new tests use in-memory SQLite or fake window fetch exclusively. They verify all three separate keys, real zero values, no leaderboard writes, dedupe/conflict/cooldown behavior, bounded frozen retries and timeout, invalid identity recovery, practice/demo/replay exclusion, and official-run boundaries in the real controllers.

Two existing inventory expectations were minimally extended for the additional keys: `tests/play-counts-repository.test.mjs` (“new empty counters and atomic concurrent same receipt only count once”) and `tests/nine-play-counts.test.mjs` (combined GET inventory). All nine older gameplay key cases remain intact.

For any browser QA, install request interception before loading pages. Block or fulfill all counter POSTs, including `/api/play-counts/views` generated by the homepage. Do not verify counters by submitting live test starts or visiting a live homepage unguarded. A deployment check can use read-only GET totals, subject to the 30-second cache.
